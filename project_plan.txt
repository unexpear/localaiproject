# Local Desktop AI Assistant Project Plan

## 1. System Reality Check

**Findings:**
- OS: Windows 11 Pro 10.0.26200
- CPU: 12th Gen Intel Core i7-12700H
- RAM: 32GB (2x16GB modules detected)
- GPU: NVIDIA GeForce RTX 3070 Ti Laptop GPU (4GB VRAM), Intel Iris Xe (1GB VRAM)
- Disk: C: 493GB free/988GB total, D: 986GB free/1TB total
- Python: 3.13.0
- Git: 2.53.0
- Ollama: Not installed or not in PATH
- No local LLM runtimes (llama.cpp, transformers, onnxruntime, etc.) detected
- No desktop UI frameworks (PyQt, PySide, Tkinter, wxPython, etc.) detected

**What this machine can run well:**
- 7B-13B LLMs with quantization (q4/q5/q8) on GPU or CPU
- Coding/Reasoning models in the 7B-13B range
- Vision models up to 7B (if RAM/VRAM allows)
- Multiple models with lazy loading

**What it can run poorly:**
- 34B+ models (VRAM limited, will OOM or be slow)
- Large vision models (VRAM limited)
- Flash Attention: Only available if compiled for GPU, not present by default
- f16 KV/cache: Not realistic for 4GB VRAM, use q8_0 or q4_K_M as default

## 8. Storage Layer Decision (2026-05-01)

**Choice: DuckDB** (https://duckdb.org/) as the embedded persistence layer
in place of JSON read-modify-write or SQLite.

### Why not SQLite
The user explicitly opted out of SQLite. The JSON-file storage that exists
today has a documented concurrent-write risk (audit finding, prior round)
because the chat handler and the install worker can both call into
`local_memory` from different threads, and `load_memory` -> mutate ->
`save_memory` does no locking.

### Why DuckDB over the alternatives

| Candidate | Verdict |
|-----------|---------|
| **DuckDB**            | MIT, embedded, ACID, modern, native Python API, single .duckdb file, supports SQL for future queries on executions/history. **Selected.** |
| LMDB                  | Excellent OLTP key-value performance + ACID, but loses SQL queryability. Better suited if we needed pure KV. |
| TinyDB + portalocker  | Minimal change but it's still JSON under the hood — the same fragility, just hidden. |
| Postgres / Cockroach  | Server-based, overkill for a single-user local app. |
| ZODB                  | Python object DB; viable but niche, smaller community. |

### Migration approach (phased)

Phase 1 (this round, low risk):
  - Add `duckdb` to requirements.
  - Build `app/memory/storage.py` -- abstract `MemoryStorage` interface.
  - Extract current JSON behaviour into `app/memory/json_storage.py`.
  - Implement `app/memory/duckdb_storage.py` with the same surface area.
  - Tests at the storage-interface level: same test suite runs against
    both backends.
  - JSON remains the active backend on disk.

Phase 2 (next round):
  - Migration script: read `local_memory.json`, write to a fresh
    `local_memory.duckdb`. Idempotent.
  - Switch `local_memory` module to delegate to the DuckDB backend.
  - Verify all callers still pass their tests.
  - Keep the JSON file as a backup until the user is comfortable.

Phase 3 (later):
  - Add SQL-backed features that were impractical with JSON:
    full-text search across executions, lane usage histograms, retention
    pruning by age, a real audit log of approval decisions.

### Constraints honoured
- Free, MIT-licensed, no commercial strings.
- Embedded -- no server process or external service.
- Single-file persistence (the `.duckdb` file lives next to the JSON
  store today and ships with the project).
- Cross-platform (Windows / macOS / Linux).
- Pure-Python install via pip, no native build steps required by the user.
